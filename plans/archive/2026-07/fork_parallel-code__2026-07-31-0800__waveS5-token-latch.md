# B：token 計算的 replay latch（S5）

**分支：** `fix/token-latch`（從 `main @ d489871` 分出）

## 問題

跨模型稽核用**真實的 `foldCodexLines`**（esbuild 打包後執行）跑八個情境，四個算錯。

`isCodexReplayEvent`（`electron/ipc/token-usage-parse.ts:609-613`）
把「不通過 replay 判定」等同於「這是活的回合」，而 `state.pastReplay = true`（`:592`）
**永久 latch**。

實測結果：

```
OK      S1 fork，累計值續接，replay < 2s          charged=200  truth=200
OK      S2 fork，replay 後累計值重啟              charged=200  truth=200
WRONG   S3 fork，replay 中一筆缺 timestamp        charged=600  truth=200   (3×)
WRONG   S4 fork，session_meta timestamp 無法解析  charged=560  truth= 60   (9×)
WRONG   S5 fork，replay 爆發跨 3.5s（> 2000ms）   charged=660  truth= 60  (11×)
WRONG   S6 fork，真實第一回合在 +1900ms（窗內）   charged= 80  truth=280  (少算)
OK      S7 一般 session 帶重試（min 封頂生效）    charged=400  truth=400
```

**S3 是最具體的**：replay 爆發中**一筆** `token_count` 記錄缺少或無法解析 `timestamp`
→ `:611` 回傳 false → `:592` latch → **剩下整段複製前綴全部被計費**。
一行壞資料就把前綴移除從「有效」變成「整個關掉」。

**S5 是系統性的**：R3b 的門檻掃描選 2000ms，理由是「這是完整命中的最小值，
所以就算漂移也是小漂移 —— 多算一兩筆而不是漏掉真實用量」。
**但那個邊界是 latch 不是 per-event**，所以漂移小不會只多算一兩筆，
而是**多算整段 replay 的剩餘部分**。較慢的磁碟、較大的母歷史、較忙的機器都會把爆發推過 2000ms。

## 現有測試的涵蓋範圍

`token-usage-parse.test.ts:723-781` 涵蓋「timestamp 全有」與「全無」
（`:764` 斷言的正是超算的結果，作為**預期行為**），以及一個剛好等於
`CODEX_REPLAY_WINDOW_MS` 的兩事件邊界案例（`:774`）。

**混合案例（部分有部分無）與跨越窗口的爆發都沒有測試。**

## 要達成什麼

**一筆無法解析的記錄不應該關掉整段前綴移除。** 判定要能區分
「這一筆無法判定」與「replay 結束了」。

怎麼做由你決定。可能方向（不是指定）：latch 需要更強的證據而非單一否定、
無 timestamp 的記錄繼承鄰近記錄的判定、或把窗口從時間改成別的訊號。

**注意稽核者自己的但書**：它的情境是合成的，而 R3b 的 D3 記錄過
「合成 fixture 漏掉了一個 784M token 的 bug，只有真實 log 抓得到」。
**所以真實 rollout 上可能不會出現 S3/S5。先用真實資料量一次再決定要不要修，
以及修法會不會改變真實數字。**

這台機器上有 262 個 codex rollout（531 MB），其中 72 個是 subagent。

## 決策紀錄

### D1 — ⚠️ 我第一版的 ground truth 是錯的，差點讓我「修好」不存在的問題

要判斷 S3／S5 在真實資料上出現幾次，得先有一個**不依賴時間規則**的
replay 長度真值。第一版沿用 R3b 的講法「與母檔共享的前導事件數」，
實作成「child.events[0..k) 與 parent.events[0..k) 逐筆相等」。

結果 74 個 fork 裡有 10 個算出 truth=0，但兩種時間規則都看到 18–146 筆的爆發。
去翻其中三個檔案才發現：**fork 重播的是母檔的一段連續區間，不是從母檔第 0 筆開始。**

```
child rollout-…019fa80e  的前 91 筆 = parent 的 events[188..279)
child rollout-…019fa7e3  的前 146 筆 = parent 的 events[90..236)
```

原因很直觀 —— 在母 session 進行到一半才 fork，重播的是「fork 當下的對話歷史」，
而母檔前面那段可能已經被壓縮掉或不屬於這條血脈。

改成「child 的前導序列在 parent 中最長的**連續**出現」之後，truth>0 的檔案
從 38 個變成 48 個，兩種規則的評分也才變得有意義。**如果沒抓到這件事，
我會拿一個錯的真值去調門檻，把規則往錯的方向調。**

### D2 — 真實資料上 S3 與 S5 都是 0 次，而這不代表不用修

三個量測（272 個 rollout、555 MB、16,794 筆 `token_count`）：

```
無法解析 timestamp 的記錄            0 / 16,794     → S3 出現 0 次
replay 爆發跨越 2000 ms 的檔案       0 / 48         → S5 出現 0 次
修法前後的計費總額                   1,010,410,406  →  1,010,410,406（差 0）
```

（1,010,410,406 這個數字與 R3b 結束摘要完全相同，代表我的量測工具復現了它的口徑。）

**所以這一波在這台機器上不改變任何數字。** 這是完整的結論，不是失敗的量測：
程式路徑無疑是錯的，但目前不可達 —— 這改變的是優先級，不是診斷。

只有一個檔案的分類在兩種規則下不同（`019fa457`：舊規則吃掉 86 筆、真值 85 筆），
而**那第 86 筆的 `last_token_usage` 全是 0**，總額因此不動。連這唯一的分歧
都不花錢，是我特地去追那一筆才確認的，不是猜的。

### D3 — 但「還沒發生」和「離得很遠」是兩回事

真實資料最寬的 replay 爆發是 **1,827 ms／141 筆記錄 —— 用掉 2000 ms 窗口的 91.3%**。
把那個檔案的時鐘拉長來定價（其餘資料不動）：

```
時鐘 ×1.0   窗口規則正常                                    多算 0
時鐘 ×1.1   1 個檔案提早 latch，5 筆重播記錄被計費          多算    982,135 tokens
時鐘 ×1.25  1 個檔案，39 筆                                 多算  6,925,422 tokens
時鐘 ×1.5   1 個檔案，74 筆                                 多算 11,660,199 tokens
```

10% 的漂移就要價將近一百萬 token。這正是 PM 指出的那件事：**邊界是 latch，
所以漂移不會只多算一兩筆。** 而 R3b 的 2000ms 是拿「完全命中的最小值」選的，
剩 8.7% 餘裕。

### D4 — 推翻 R3b 的「取最小值」，改取**最大**的完全命中值

這是我唯一一次反過來推翻既有決定的地方，理由是**代價的方向變了**。

R3b 的原話：「取 2000 ms 是完全命中的最小值，所以萬一 drift 也是往偏小倒
（多算一兩筆複製的），而不是往偏大倒（丟掉真實用量）。」
這對**逐筆判定**成立，對**會 latch 的邊界**不成立 —— 偏小不是多算一兩筆，
是多算整段剩餘。

換成 gap 之後兩邊的代價要重新定價，實測（48 個有重播的 fork）：

```
爆發內部的 gap             6,609 筆   p99   6 ms   max     85 ms
session 起點 → 第一筆重播     48 檔               max    157 ms
第一筆必須算「活的」的 gap    73 檔   min 3,214 ms
```

（第 74 筆的 live gap 是 765 ms，但**那筆記錄的 token 全是 0**，落在邊界哪一側
都不影響任何數字，所以不該拿它當門檻的約束條件。這一點是查出來的：
它就是 D2 裡 `019fa457` 那筆。）

- **門檻太小** → 爆發被中途切斷，剩下整段被計費（若切在第一筆，整段爆發都被計費）
- **門檻太大** → 吞掉一筆真實 turn，而下一個多秒的 gap 馬上就會結束 replay

**太大只花一筆，太小花剩下全部。** 所以取**最大**的完全命中值：**750 ms**。
200–750 ms 全部 74/74，1000 ms 開始失分。750 ms 是內部 gap 上限的 8.8 倍、
起點 gap 上限的 4.8 倍，同時仍是最快帶 token 的真實 turn 的 1/4.3。

### D5 — 邊界改「與前一筆的距離」，不是「距 session 起點的時間」

窗口規則有兩個獨立的問題，只修 latch 不夠：

1. 它是**全域量**：母歷史越大、磁碟越慢，爆發就越寬，遲早撞線（D3）
2. 它會**吃掉窗內的真實第一回合**（稽核者的 S6）—— 真實資料裡就有一個
   `019fa457`，舊規則吃掉第 86 筆

改成「與前一筆記錄的距離 ≤ 750 ms 就還在同一個爆發」之後，兩個都不成立：
爆發要多長有多長（因為判斷是局部的），而 +1900 ms 才出現的真實回合
距離前一筆有 1900 ms，直接判為活的。實測 74/74 完全命中，窗口規則是 73/74。

**誠實的但書**：新規則**仍然是 latch**（一旦判定活的就永不回頭，這是 `:751`
要求的行為）。改變的是「觸發 latch 所需的證據強度」：從 1827 vs 2000 ms
（8.7% 餘裕）變成 85 vs 3,214 ms（38 倍分離），而且**無法判定的記錄再也不會觸發它**。

### D6 — 三值分類，不是布林值

核心修正就這一句：`isCodexReplayEvent` 回傳 boolean，把「這筆無法判定」
和「replay 結束了」壓成同一個 `false`。改成 `'replay' | 'live' | 'unjudgeable'`：

- `unjudgeable`（沒有時間戳，或還沒有任何參考時鐘）→ **照算**（維持
  「寧可多算複製的、也不要漏掉真實的」偏向），但**不設 `pastReplay`**，
  爆發從它旁邊繼續走
- 只有 `live` 才 latch

代價因此從「剩下整段」變成「這一筆」—— 這正是 PM 說 2000 ms 當初**以為**
自己有的性質。順帶把 S4（session 時鐘無法解析）也一起收斂：第一筆無從比較
所以照算，然後**它自己的時鐘成為後面那些記錄的參考點**，剩下的爆發照樣被扣掉。

### D7 — 為什麼不加「絕對上限」當保險

想過在 gap 規則之外再壓一個「replay 不得超過 session 起點後 N 秒」的天花板，
擋住「一連串又快又真」的極端情況。**放棄了**：那個天花板就是 2000 ms 窗口的
放大版，母歷史夠大時照樣會撞，而撞上去的代價一樣是剩下整段。
與其加一個遲早會失效的全域界線，不如接受「規則完全是局部的」這個性質，
並把它寫進註解裡。

### D8 — 沒有動的東西

`electron/ipc/token-usage.ts` 一行沒動：新的 `replayAtMs` 預設 `null`，
需要參考點時才回退到 head probe 已經填好的 `sessionStartMs`，
所以增量讀取路徑與 head probe 的既有 seeding 完全不受影響。
`offline.ts`／`PRIVACY.md`／`docs/PRD.md` 一字未動，`OUTBOUND_SURFACES` 維持 11。

## 結束摘要

### 先講量測（它決定了這一波有多重要）

在 272 個 codex rollout（555 MB、16,794 筆 `token_count`）上：

- **S3（爆發中有記錄缺／壞 timestamp）：0 次。** 整批資料裡沒有任何一筆
  `token_count` 的 timestamp 無法解析。
- **S5（爆發跨越 2000 ms）：0 次。** 最寬的是 1,827 ms。
- **修法前後總額：1,010,410,406 → 1,010,410,406，差 0 tokens（0.0000%）。**

**這一波在這台機器上不改變任何一個數字。** 稽核者的但書是對的 —— 它的情境是合成的，
而真實資料上這條路徑目前不可達。但它同時也**不是安全的**：最寬的真實爆發用掉了
2000 ms 窗口的 91.3%，把那個檔案的時鐘拉長 10% 就要多算 982,135 tokens，
拉長 50% 要多算 11,660,199 tokens。所以修的理由不是「現在算錯了」，
而是「錯的條件只差 8.7%，而且踩到的代價是整段而不是一兩筆」。

### 做了什麼

`isCodexReplayEvent`（boolean）換成 `placeCodexEvent`（三值）：

1. **`unjudgeable` 不再等於 `live`。** 無法判定的記錄照算（一筆的代價），
   但不設 `pastReplay`，爆發繼續。一行壞資料再也不能把前綴移除整個關掉。
2. **邊界從「距 session 起點」換成「距前一筆記錄」**，並新增 `replayAtMs`
   當爆發自己的時鐘。判斷變成局部的，爆發要多長有多長。
3. **門檻重新推導為 750 ms**（原 2000 ms）：因為代價的方向反過來了，
   取最大的完全命中值而不是最小值。實測 74/74，舊規則 73/74。
