agy 的三個假陽性有共同形狀：**把文件明文寫出的範圍界線當成未覆蓋的缺口**

**它沒有讀過那十七波的決策脈絡**，看到的是靜態程式碼。所以產出必須逐項查證，不能整批採信。

#### 最有價值的三個發現

1. **PEM 私鑰本體完整落地，而事件被標記 `redacted`**（三家都指出）。
   規則只匹配標頭、沒有下游丟棄邏輯。**比沒有規則更危險 —— 標記是「已處理」的肯定宣稱。**
2. **`token-usage-parse.ts:280` 含字面 NUL byte**（`\0` 哨兵），`rg` 判成 binary
   並印 `binary file matches` 卻**不顯示任何行**，除非加 `-a`。1,936 行對所有沒加 `-a`
   的搜尋隱形。**PM 自己的「零網路」查證就中過這一招**（結論仍成立，但那是運氣不是方法）。
3. **`preload-allowlist.test.ts:28-29` 的三方比對是同義反覆。**
   `channels.ts:3` 是 `export const IPC = channelManifest`，所以 `IPC` 與 manifest
   的比對是拿自己比自己，**永遠不會失敗**。真正在做事的只有 preload 那半。
   PM 在十幾份規格裡都寫「斷言三者是精確集合」—— **那句話講大了守衛的涵蓋範圍。**

### 驗收時一定要做的八件事

全部是實測或追程式碼才浮現的，**沒有一件是讀回報或讀 diff 看得出來的**。

1. **`git log main..<branch>` 確認 commit 真的存在。** 十波裡有五波宣稱完成而分支停在起點
   （其中一次是我誤判 —— pre-commit hook 正在跑，不是假回報，查看時要留意時序）。
2. **新測試單獨跑一次**：`vitest run <file> -t "<describe>"`。
   根因是 `vi.clearAllMocks()` 只清呼叫紀錄、不清 implementation（那要 `resetAllMocks`），
   前一個測試設的 `mockResolvedValue` 會黏著給後面借用。整檔綠、單跑紅。
3. **測試斷言的常數要從 production 模組 import**，不能複製字串。
   否則常數一改，測試就從此不證明任何事。
4. **entry chunk 百分比下降時，先問那個 chunk 有沒有被 `modulepreload`。**
   把程式碼搬到有 preload 的兄弟 chunk，`check:bundle` 數字會降但使用者付的成本不變 ——
   對 gate 為真、對使用者為假。
5. **接線超過一跳時，要有跨邊界的測試。** MCP server 是獨立 Node 行程經 REST 跟 app 對話，
   `handleCreateTask` 是逐欄位手寫轉發 —— **沒讀到的欄位直接消失，而四道 gate 全綠**。
   型別檢查過（欄位只是沒被讀）、lint 過、架構檢查過、測試也過。
6. **合併若是 no-op 就不要 commit。** 無條件 `git commit` 會把 lint-staged 留在 index 的
   殘留掃進去，並冠上假的合併訊息。
7. **`rg` 可能靜默跳過整個檔案。** 含 NUL byte 的檔案會被判成 binary，印
   `binary file matches` 但不顯示內容 —— 接 `| head` 或只看有無結果時會被當成「有找到」。
   **搜尋結果為零時，加 `-a` 再確認一次。**
8. **「規則觸發」不等於「內容被移除」。** 遮蔽／過濾類的程式碼要分開驗兩件事：
   規則有沒有匹配、以及匹配到的東西是不是真的不見了。只驗前者的測試會讓後者永遠不被發現。

### 稽核找出的九項 —— 全數修畢

修的過程中有三項的**診斷被推翻**，值得留著：

- **S7 不是同義反覆。** 稽核者說「拿自己比自己、永遠不會失敗」，實測是錯的 ——
  `IPC_MANIFEST` 是 `createRequire` 獨立讀一次 JSON。真正的問題只是**測試名稱說「三方」
  而手工維護的產物只有兩個**。修法反而把它從 `Object.values` 強化成完整 key→value 映射。
  **PM 當時採信稽核者、未實測就向 Scott 更正 —— 那是這批唯一一次沒查證就轉述。**
- **S8 不是架構限制造成的。** 稽核者猜 `shared/` 不能 import `mcp/`；實測加了 import
  跑 gate 是 `✔ no violations`，所以複製常數是疏忽。常數仍然搬到 `shared/`，
  但理由是「`mcp/ → shared/` 有 9 條邊、反向 0 條，而反向邊沒有任何 gate 擋得住」。
- **S3 的機制跟大家以為的不同。** 不是負載拖慢測試讓自己的 timer 燒到，
  而是 **worker fork 被下一個測試檔重用**；單獨跑時行程先死、timer 被靜默丟棄 ——
  這正是兩波之前在閒置機器上量到「無害」的原因。移除呼叫點實際有 **8 個**不是 6 個，
  這解釋了那個沒人說得出原因的「6 變 10」變異。

### R1 — Onboarding（Q2 已裁決 2026-07-31：維持進階功能，不進主路徑）

**現況**：這個 app 沒有 onboarding，只有空狀態。`TilingLayout.tsx:482` 的
「Link your first project to get started」與 `Sidebar.tsx:698` 的「No projects linked yet.」
就是全部。Coordinator 是 `NewTaskDialog` 裡的一個 checkbox，Arena 在 `SidebarFooter`。

**建議：Coordinator 與 Arena 維持進階功能，不進 onboarding 主路徑。** 三個理由：

1. PRD 自己把 Arena 全部標為 **P2**，Coordinator 的 `FR-COORD-01`～`09` 幾乎都是 P0
   且大半在講失敗處理（MCP server 起不來、控制權切換失敗、token 越權）。
   把最難的失敗模式擺在新使用者面前，是最容易流失的地方。
2. 產品的核心價值（PRD §5.1）是「單一任務的 worktree 隔離」。第一次使用要成立的是這件事。
3. Coordinator 需要 MCP server + token wiring 才能啟動，那是唯一會因為環境問題整段失敗的路徑。

**做法：三階段漸進揭露，不做 wizard。**

| 階段       | 觸發                     | 揭露什麼                                                 |
| ---------- | ------------------------ | -------------------------------------------------------- |
| 1 首次成功 | 尚未 merge 過任何 task   | 連結專案 → 建立一個 task → 看 diff → merge。其餘入口收起 |
| 2 平行     | 已完成第一次 merge       | 提示可以同時開多個 task（這才是產品名字的意思）          |
| 3 進階     | 已同時跑過 2 個以上 task | 才顯示 Coordinator 與 Arena 的說明入口                   |

實作上**不引入 wizard 框架**：把既有空狀態串成序列，狀態存一個
persisted flag（`state.json` 已有 rolling backup 機制，沿用即可）。
新邏輯放 `src/lib` 當純函式 —— vitest 是 node 環境，component 層測不到。
